# Portable repro archive retention

`enforce_repro_archive_retention` applies bounded retention directly to transported repro ZIPs without trusting filenames or extensions as evidence of validity.

Only direct-child regular files that successfully traverse the canonical `import_repro_archive` validator are eligible. Retention first reads one bounded immutable snapshot of each candidate and runs that exact snapshot through the importer, so the transport digest, byte accounting, and semantic validation all describe the same bytes. Validation enforces the per-archive byte budget, exact member set, regular uncompressed members, bounded input/manifest sizes, and the normal repro bundle schema and digest checks. Directories, symlinks, unrelated files, malformed archives, and tampered bundles are reported as `ignored` and are never intentionally deleted.

Eligible archives are ordered newest-first by file mtime, with filename as a deterministic tie breaker. At most `max_archives` are retained. Callers may also set `max_total_archive_bytes` to bound aggregate retained transport storage. The aggregate budget is applied greedily in newest-first order: an eligible archive that would exceed the remaining byte budget is selected for removal, while a later smaller archive may still be retained if it fits. `None` preserves the count-only behavior. Both limits accept zero and reject booleans, negative values, and other invalid types before directory scanning.

Before unlinking an over-budget archive, retention re-reads the direct-child entry without following symlinks and compares its regular-file identity with the device, inode, mode, size, mtime, and ctime captured at validation. If the pathname disappeared, no deletion is needed. If the entry changed identity, became a non-regular file, or cannot be safely restated, retention does not unlink it and reports the path as `ignored` rather than `removed`. This guard is deliberately fail-closed for detected replacement and avoids deleting unrelated content that arrived at the same pathname after validation. It is not a filesystem lock and does not claim to eliminate an adversarial race after the final identity check.

Callers that retain evidence from multi-signature fuzz or fault campaigns may opt into `preserve_unique_failures=True`. In that mode, retention validates and loads each archive's stable `FailureSignature`, then makes a first newest-first pass that retains at most one archive per distinct signature while count and aggregate-byte capacity remain. Archives whose signature is already represented are deferred until the diversity pass is complete, then considered newest-first for any remaining capacity. If the newest archive for a signature does not fit the byte budget, a later smaller archive with that same signature remains eligible to represent it. This policy does not infer failure identity from filenames, metadata, or diagnostic text.

Archive sizes used for retention accounting are the lengths of the exact immutable snapshots that passed canonical validation. Every retained item therefore has one `ArchiveRetentionEvidence` record containing its path, snapshot byte length, SHA-256 transport digest, and validated stable failure signature. `ArchiveRetentionResult.kept_evidence` has the same order as `kept`. Existing `kept`, `removed`, and `ignored` path tuples remain available.

Consumers should pass `evidence.archive_sha256` to `replay_repro_archive(..., expected_archive_sha256=...)`. That creates a fail-closed handoff across the retention/replay boundary: if another actor replaces the retained path after the retention pass, replay rejects the changed transport before bundle import, replay-context checks, or candidate/oracle execution. The retention pass does not claim to make the directory immutable; it supplies the identity needed for a later consumer to detect path replacement.

Integration coverage creates real candidate/oracle repros with distinct stable failure signatures, proves a newer duplicate cannot evict the only retained evidence for another signature when diversity preservation is enabled, replays retained transports with their captured SHA-256 pins, proves a post-retention retained-path replacement is rejected before a marker child process can launch, and proves a removal candidate replaced with another valid repro archive is preserved and remains replayable through real child processes.

This capability intentionally does not recurse, infer validity from `.zip` suffixes, delete malformed evidence, execute candidate/oracle targets while deciding retention eligibility, make signature diversity override the configured count or byte ceilings, or provide filesystem locking against concurrent writers.
