# Post-exit descendant cleanup

`run_process` treats target code as untrusted. A root target may spawn descendants and then exit before they do. Waiting indefinitely for descendants that retain stdin, stdout, or stderr would let a target escape the runner timeout after its root process has already terminated. A descendant can also redirect all inherited stdio and remain alive after the root exits, which must not silently turn a process-isolated test into a background workload.

After the root exits, the runner therefore keeps post-exit cleanup bounded. On POSIX each target starts in its own session. The runner probes that dedicated process group after reaping the root; if any member remains, the run is classified as an infrastructure failure with `ProcessTreeLeak` and the group is killed even when every stdio worker has already drained.

On Windows each successfully launched target is immediately assigned to a private Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. After the root is reaped, the runner queries the job's active-process count. Any remaining process is a descendant leak even when it redirected stdin/stdout/stderr away from the harness; the run is classified as `ProcessTreeLeak` and the entire job is terminated. Closing the job handle is a final containment backstop. Failure to create, configure, assign, or query the Job Object is treated as a `WindowsJobError` infrastructure failure rather than silently dropping to weaker isolation.

The bounded stdio-drain path remains as a second guard on every platform. Windows also retains the existing shell-free `taskkill /T /F` path as a fallback when no usable Job Object is available or Job Object termination itself fails. The helper invocation has a one-second timeout; if `taskkill` times out, cannot start, or returns failure while the root is still alive, the runner falls back to `Popen.kill()` so cleanup cannot block indefinitely inside the operating-system helper.

Timeout and output-budget termination also keep root reaping bounded. Once tree termination has been requested, the runner waits at most one second for the root to become reapable, makes one direct `Popen.kill()` attempt if necessary, and waits at most one additional second. A root that still cannot be reaped is reported as `ProcessTerminationTimeout` instead of turning a target timeout into an unbounded `wait()` inside the harness. Natural exits still use the normal reap path after `poll()` has already reported completion.

These classifications are intentionally distinct from product mismatches: a descendant outliving the target root, a containment setup/query failure, or a root that cannot be reaped after forced cleanup is an execution-environment failure, not target output that an oracle should compare.

Focused regressions launch real Python targets for the bounded cleanup paths. One descendant inherits the harness pipes and proves post-exit draining remains bounded. A POSIX descendant redirects stdin/stdout/stderr to `DEVNULL`, sleeps, and attempts a delayed marker write; the runner must detect the surviving process group, kill it, report `ProcessTreeLeak`, and prevent the marker from being created. Windows CI now exercises the same redirected-stdio escape attempt through a real Job Object and requires the same `ProcessTreeLeak` classification and marker suppression. A separate Windows self-test assigns a real sleeping process to a Job Object, observes its active-process count, terminates the job, and verifies the count returns to zero. Windows CI also keeps the `taskkill` timeout regression to prove direct root termination remains bounded when that fallback helper stalls. The termination-reap regression exercises a real sleeping Python target through the public timeout path and separately verifies that a first reap timeout triggers the direct-kill retry contract.

The POSIX group check covers descendants that remain in the dedicated target session/process group. A descendant that deliberately creates a new session can still escape that POSIX operating-system boundary; preventing that requires a stronger primitive such as a cgroup/container. On Windows, Job Object membership is inherited by ordinary child processes, so redirecting stdio or creating a new process group does not by itself escape containment. Processes explicitly launched with breakaway rights remain an operating-system policy boundary and are not granted by this runner.
