# SQLite WAL crash recovery conformance

`SQLiteWALCrashRecoveryTarget` validates two bounded real SQLite process-crash recovery contracts over one file-backed WAL database. By default, an uncommitted writer that is force-terminated after acquiring the write transaction must not publish its update. With `commit_before_crash=True`, the complementary contract is exercised: a writer commits its update, reports a deterministic post-commit checkpoint, and is force-terminated before normal connection close; reopening the database must still observe that committed value. In both modes the database must remain writable after recovery.

The process-isolated target creates a real temporary file-backed WAL database with committed value `0`, disables automatic checkpointing, then launches a separate writer process with argv-only `subprocess.Popen`. The writer opens an independent connection, executes `BEGIN IMMEDIATE`, and updates the row to `1`. In the default mode it emits `UNCOMMITTED_READY` without committing. In committed mode it first commits and only then emits `COMMITTED_READY`. The parent force-terminates the writer only after the selected handshake and waits for the process to exit before reopening the same database.

Default recovery must observe the previously committed value `0`; committed-mode recovery must observe value `1`. The reopened connection must then be able to acquire a fresh write transaction, commit value `2`, and read `2` back. The committed-mode option is encoded in the `CommandTarget` argv, so it participates in target/replay identity instead of being hidden process state. The emitted JSON transcript records only stable semantic observations rather than platform-specific process exit codes or WAL frame/layout details, so repeated executions can be compared through `DifferentialHarness`.

The target accepts no test-program input. Any non-empty stdin is rejected before database work. It never interpolates input into a shell command. The outer `CommandTarget` continues to own timeout, output-budget, process-tree cleanup, and infrastructure-failure classification for the target process.

This slice proves SQLite process-crash behavior after an acknowledged transaction commit; it does not claim power-loss durability, storage-controller cache persistence, fsync guarantees under hardware failure, torn-write behavior, corruption recovery, checkpoint recovery, or byte-identical WAL layout. Those require separate bounded integrations with stronger storage/fault control.
