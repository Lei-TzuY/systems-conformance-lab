# SQLite WAL crash recovery conformance

`SQLiteWALCrashRecoveryTarget` validates bounded real SQLite process-crash recovery contracts over one file-backed WAL database. By default, an uncommitted writer that is force-terminated after acquiring the write transaction must not publish its update. With `commit_before_crash=True`, the complementary contract is exercised: a writer commits its update, reports a deterministic post-commit checkpoint, and is force-terminated before normal connection close; reopening the database must still observe that committed value. In both modes the database must remain writable after recovery.

With `recover_in_child=True`, the first post-crash recovery observation is performed by a fresh independent Python process rather than only by the orchestration process. After the writer is force-killed, that observer opens the same file-backed WAL database through argv-only execution and must see the expected recovered value (`0` after an uncommitted crash, `1` after an acknowledged committed crash). The orchestration process then independently reopens the database and continues the normal post-recovery writeability checks. This proves the persisted WAL state is consumable across a real process lifetime boundary, not merely by another connection in the original target process.

With `pin_reader_snapshot=True`, the target also opens an independent reader transaction before the writer starts and pins value `0` into that reader snapshot. After the writer reaches the selected committed or uncommitted checkpoint and is force-killed, the pinned reader must still observe `0`, while a fresh connection must observe the correct recovered value (`0` for an uncommitted crash, `1` for a committed crash). A new write transaction then commits value `2` while the old reader remains open; the old reader must still observe `0`. Only after the reader transaction is released may that connection lifetime end, at which point a fresh observation must see `2`.

With `checkpoint_after_crash=True`, the target deepens the committed crash path into a checkpoint-recovery lifecycle. This mode requires both `commit_before_crash=True` and `pin_reader_snapshot=True`. After the committed writer is force-killed and a fresh connection confirms value `1`, `PRAGMA wal_checkpoint(TRUNCATE)` must report busy while the pre-crash reader still pins value `0`. A fresh writer must nevertheless commit value `2` while that reader remains open. After the reader releases its snapshot, the same truncating checkpoint must complete without busy and value `2` must remain visible. The transcript records only the stable busy/not-busy semantics rather than WAL frame counts, which may vary across SQLite builds.

With `checkpoint_in_child=True`, both truncating-checkpoint attempts are executed by fresh independent Python processes instead of by the orchestration connection. This mode requires `checkpoint_after_crash=True`. The first child opens the same WAL database while the pre-crash reader transaction remains pinned and must report busy. After the orchestration process commits value `2` and releases that reader snapshot, a second fresh child must run the truncating checkpoint without busy. Each child is launched through a fixed argv-only module invocation, with stdin disconnected, stdout/stderr captured, and an explicit timeout. Only the stable `0`/`1` busy result crosses the process boundary; WAL frame counts remain deliberately excluded from the conformance transcript.

With `integrity_check_in_child=True`, the completed crash/checkpoint lifecycle is additionally validated by a fresh independent process running `PRAGMA integrity_check` against the recovered database. This mode requires `checkpoint_after_crash=True`, so the check runs only after the pinned reader has been released, the post-crash write of value `2` has committed, and the formerly blocked truncating checkpoint has completed. The child must receive exactly one `ok` result; any other row set, stderr output, non-zero exit, malformed stdout, or timeout fails the target. This adds a structural database-consistency invariant across the crash and checkpoint boundary rather than relying only on one row's logical value.

The process-isolated target creates a real temporary file-backed WAL database with committed value `0`, disables automatic checkpointing, then launches a separate writer process with argv-only `subprocess.Popen`. The writer opens an independent connection, executes `BEGIN IMMEDIATE`, and updates the row to `1`. In the default mode it emits `UNCOMMITTED_READY` without committing. In committed mode it first commits and only then emits `COMMITTED_READY`. The parent force-terminates the writer only after the selected handshake and waits for the process to exit before recovery observations continue. When enabled, the recovery observer, checkpoint workers, and integrity worker are also launched with fixed argv-only module invocations, bounded by explicit subprocess timeouts, with stdin disconnected and stdout/stderr captured for strict result validation.

Default recovery must observe the previously committed value `0`; committed-mode recovery must observe value `1`. The recovered connection must then be able to acquire a fresh write transaction, commit value `2`, and read `2` back. When reader pinning is enabled, that write occurs while the original reader transaction is still alive, proving WAL's reader/writer concurrency contract survives the crash boundary. `commit_before_crash`, `pin_reader_snapshot`, `checkpoint_after_crash`, `checkpoint_in_child`, `recover_in_child`, and `integrity_check_in_child` are encoded in the `CommandTarget` argv, so they participate in target/replay identity instead of being hidden process state. The emitted JSON transcript records only stable semantic observations rather than platform-specific process exit codes or WAL frame/layout details, so repeated executions can be compared through `DifferentialHarness`.

The target accepts no test-program input. Any non-empty stdin is rejected before database work. It never interpolates input into a shell command. The outer `CommandTarget` continues to own timeout, output-budget, process-tree cleanup, and infrastructure-failure classification for the target process.

This slice proves SQLite process-crash behavior, cross-process recovery observation, reader-snapshot isolation, bounded truncating-checkpoint recovery, and optional independent structural integrity validation after that lifecycle. It does not claim power-loss durability, storage-controller cache persistence, fsync guarantees under hardware failure, torn-write behavior, corruption recovery, or byte-identical WAL layout. Those require separate bounded integrations with stronger storage/fault control.
