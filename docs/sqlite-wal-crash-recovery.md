# SQLite WAL crash recovery conformance

`SQLiteWALCrashRecoveryTarget` validates bounded real SQLite process-crash recovery contracts over one file-backed WAL database. By default, an uncommitted writer that is force-terminated after acquiring the write transaction must not publish its update. With `commit_before_crash=True`, the complementary contract is exercised: a writer commits its update, reports a deterministic post-commit checkpoint, and is force-terminated before normal connection close; reopening the database must still observe that committed value. In both modes the database must remain writable after recovery.

With `pin_reader_snapshot=True`, the target also opens an independent reader transaction before the writer starts and pins value `0` into that reader snapshot. After the writer reaches the selected committed or uncommitted checkpoint and is force-killed, the pinned reader must still observe `0`, while a fresh connection must observe the correct recovered value (`0` for an uncommitted crash, `1` for a committed crash). A new write transaction then commits value `2` while the old reader remains open; the old reader must still observe `0`. Only after the reader transaction is released may that connection lifetime end, at which point a fresh observation must see `2`.

With `checkpoint_after_crash=True`, the target deepens the committed crash path into a checkpoint-recovery lifecycle. This mode requires both `commit_before_crash=True` and `pin_reader_snapshot=True`. After the committed writer is force-killed and a fresh connection confirms value `1`, `PRAGMA wal_checkpoint(TRUNCATE)` must report busy while the pre-crash reader still pins value `0`. A fresh writer must nevertheless commit value `2` while that reader remains open. After the reader releases its snapshot, the same truncating checkpoint must complete without busy and value `2` must remain visible. The transcript records only the stable busy/not-busy semantics rather than WAL frame counts, which may vary across SQLite builds.

The process-isolated target creates a real temporary file-backed WAL database with committed value `0`, disables automatic checkpointing, then launches a separate writer process with argv-only `subprocess.Popen`. The writer opens an independent connection, executes `BEGIN IMMEDIATE`, and updates the row to `1`. In the default mode it emits `UNCOMMITTED_READY` without committing. In committed mode it first commits and only then emits `COMMITTED_READY`. The parent force-terminates the writer only after the selected handshake and waits for the process to exit before recovery observations continue.

Default recovery must observe the previously committed value `0`; committed-mode recovery must observe value `1`. The recovered connection must then be able to acquire a fresh write transaction, commit value `2`, and read `2` back. When reader pinning is enabled, that write occurs while the original reader transaction is still alive, proving WAL's reader/writer concurrency contract survives the crash boundary. `commit_before_crash`, `pin_reader_snapshot`, and `checkpoint_after_crash` are encoded in the `CommandTarget` argv, so they participate in target/replay identity instead of being hidden process state. The emitted JSON transcript records only stable semantic observations rather than platform-specific process exit codes or WAL frame/layout details, so repeated executions can be compared through `DifferentialHarness`.

The target accepts no test-program input. Any non-empty stdin is rejected before database work. It never interpolates input into a shell command. The outer `CommandTarget` continues to own timeout, output-budget, process-tree cleanup, and infrastructure-failure classification for the target process.

This slice proves SQLite process-crash behavior, reader-snapshot isolation, and a bounded truncating-checkpoint recovery path after an acknowledged transaction commit. It does not claim power-loss durability, storage-controller cache persistence, fsync guarantees under hardware failure, torn-write behavior, corruption recovery, or byte-identical WAL layout. Those require separate bounded integrations with stronger storage/fault control.
