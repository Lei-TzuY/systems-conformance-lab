# SQLite WAL committed writer crash after partial reader release

`SQLiteWALPartialReleaseCommittedWriterCrashTarget` validates a durability and retention boundary that combines independent WAL reader lifetime with a writer process crash **after** a successful commit.

The target uses a real temporary file-backed SQLite database in WAL mode. An older reader pins snapshot `60`; a writer commits `61`; a newer reader pins snapshot `61`; and another writer commits `62`. A truncating checkpoint must be busy while both readers are pinned. The newer reader is then force-killed, after which the older reader must still see snapshot `60` and must continue to keep the truncating checkpoint busy.

Next, an independent writer process executes `BEGIN IMMEDIATE`, updates the row to `63`, commits, emits a fixed `COMMITTED 63` readiness record, and remains alive. Only after the parent has observed that post-commit record is the writer process force-killed. This ordering distinguishes the contract from uncommitted-writer rollback coverage: the durable transaction has crossed the SQLite commit boundary before process death.

After the committed writer dies, the surviving older reader must still observe snapshot `60`, while a fresh observer must see committed value `63`. The truncating checkpoint must remain busy because the older reader still owns its snapshot; killing a writer after commit must not accidentally release another process's WAL reader state. Only after the older reader is also force-released may the truncating checkpoint complete non-busy.

A fresh reopen then verifies value `63` and `PRAGMA integrity_check = ok`. A follow-up writer commits `64`; another fresh reopen must observe durable value `64`, integrity `ok`, and a non-busy final checkpoint.

The outer target rejects non-empty test-program input. All subprocess launches use fixed argv with `shell=False`; the database path and committed value passed to the internal writer are generated by the target itself rather than interpreted from untrusted test input. The normal `CommandTarget` runner supplies bounded execution time, output limits, process-tree cleanup, and infrastructure-failure classification.

This slice proves that a committed WAL transaction remains visible and durable across immediate writer-process death while an older surviving reader retains its own snapshot and checkpoint constraint. It does not claim power-loss durability, torn-write recovery, storage-controller cache persistence, or byte-identical WAL layout.
